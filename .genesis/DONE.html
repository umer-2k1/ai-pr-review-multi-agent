1 · The Locked Spec (what we are building)

Cognitive job: Perform the reasoning a careful senior engineer performs on a pull request — and prove its work. Fan a diff out to four specialist reasoners (security, quality, tests, docs) running in parallel, each returning structured Finding objects carrying confidence and rationale. An aggregator merges the four lanes, deduplicates by file+line, computes an overall_confidence, and produces a draft review that a human approves before anything is posted. Every action is appended to a time-ordered events spine.

Inputs: a unified diff, the contents of the files it touches, and repo conventions  →  Outputs: a deduplicated, severity-ranked Finding[] plus a draft review in markdown, and one event row per action

Autonomy level: Level 2 — “Human reviews output” (study §0.3). Chosen because consequence-of-error is high (a missed vulnerability), the system is brand-new and has earned no trust yet, and it is far easier to remove a checkpoint later than to recover from removing it too early.  |  Human-in-the-loop points: exactly one, and it is the publish gate — the agent drafts, a human approves, only then does anything reach the PR. Enforced twice: in code (INV-4) and at the credential layer (read-only token).

Failure tolerance: degrade to slower-but-correct, never fast-but-wrong. A specialist that errors or times out produces a partial review explicitly flagged incomplete; the aggregator never silently drops a lane and never reports a crashed specialist as a clean result. The named primary risk is the study’s “almost-right” problem (§0.2): 90%-correct reviews that lull the reader into rubber-stamping — which is why confidence and rationale are required fields, not optional ones.  |  Trust boundary: internal/private repo, so diff authors are trusted teammates — but the diff is still untrusted input to an LLM, and dependency updates or generated code can carry injected instructions. Diff content is never allowed to escalate the agent’s privileges, and the agent holds no write scope to escalate to.

2 · Definition of Done (binary gates — checked by the VERIFIER, not the maker)

Dependency direction inward, zero cycles (modular-architecture gate)
Every outbound call has a timeout / circuit-breaker (production-readiness gate)
All LLM/structured outputs validated against a schema (llmops gate)
Threat model written; prompt-injection / untrusted-input considered (security gate)
mypy src/ clean AND pytest -q green in CI
One verify pass by a separate agent/model (L4)
No context-graph.json invariant violated by the change

A milestone is DONE only when every box above is checked by the verifier. Pull each gate from the relevant agentic-swe-master phase gate.

Project-specific gates — lifted from the study’s own phase gates (§4.1) for the phases this scope actually passes through, plus the invariants written at G2.

Phase 8 · Multi-Agent — 4 specialists + contracts + aggregator produce one review
Phase 5 · LLM & Reasoning — every specialist returns schema-valid structured output; prompts are versioned, not inline
Phase 19 · HITL — the approval gate is wired and a CRITICAL finding forces HOLD regardless of confidence
Phase 10 · Observability — every action lands on the events spine with tokens + duration
Phase 12 · Reliability — a forced specialist failure yields a flagged partial review, never a crash and never a false clean
INV-3 grounding — zero findings cite a file/line absent from the parsed diff
INV-4 no unattended write — no code path posts to GitHub without human approval

Deliberately excluded from this scope's definition of done (study phases 2, 3, 6, 13, 14, 16, 17, 20): webhook + HMAC idempotency, Redis/ARQ queue, pgvectorscale RAG, Tiger Cloud provisioning, continuous aggregates, Next.js dashboard. Excluded ≠ rejected — these are the documented graduation path if the prototype earns it.

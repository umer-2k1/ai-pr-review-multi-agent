What M1 actually built

A pull-request diff goes in; grounded, schema-valid Finding objects come out — with no network, no API key, and no GitHub access.

The one idea that makes the rest work

Structured output turns the next step into data processing. Because every specialist returns Finding objects rather than prose, the aggregator (M2) can deduplicate by (file_path, line_start), and the HITL gate (M3) can threshold on a number. Against four blobs of English, neither is possible. This is why PLAN.md's brainstorm rejected the "one big reviewer" approach outright: prose cannot be thresholded, deduped, or evaluated.

Grounding is enforcement, not prompting. The prompt asks the model to cite only visible lines; is_grounded() then checks, and drops what fails. Asking politely is not a control.

What went wrong — the six review rounds

Every defect below was found by a separate opus-5 verifier, not by the maker, and every one was reproduced before being fixed. Three were introduced by earlier fixes.

Round 1 — five defects

B3, the worst: is_grounded() tested overlap, not containment. A finding claiming lines 1..100000 passed against a hunk of 10..23 — neither endpoint real — because the range straddled it. The CLI then printed app/db.py:1, a location that does not exist. The hole was inside the function implementing the anti-hallucination invariant.

Same line also enumerated every line in the range: a 5M-line range took 2.11s, so a model emitting line_end: 1000000000 buys minutes of dead spin. Now containment-only, O(hunks).

B2: the fixture was a corrupt patch — git apply --check said so — whose hunk headers over-claimed their bodies. Every INV-3 test was validated against a fixture that was itself lying. Regenerated from real git diff.

Round 2 — a regression from round 1's own fix

BD-1: Round 1 guarded the file-header check with "am I inside a hunk?", inferred from line prefixes. But git renders a deleted line starting -- as --- <content> — identical in prefix to a file header. The hunk ended early and the next added line beginning ++ was read as a new file:

paths: ['mig.sql', 'phantom.py']
  mig.sql    added: {}                            ← real file, content lost
  phantom.py added: {3: 'password = "leaked"'}    ← invented file

A credential, in the security lane, on a valid patch. INV-3 still passed, because nothing ungrounded was shown — the finding was simply gone. Lesson: prefixes cannot separate content from structure in this format. Hunk headers declare their length; count instead.

Rounds 3–5 — one root cause, chased through three layers

The same bug wore three costumes: characters Python treats as structure but a diff treats as content.

RoundWhereSymptom
3splitlines() in the parserA form feed split an added line in two; content lost, numbers shifted.
4render_for_prompt()Unescaped content broke the <line_no>: framing; a CRITICAL landed on an unmodified context line.
5read_text() in the CLIUniversal-newline mode rewrote a lone \r to \n before the parser ran.

Round 5 is the instructive one. The parser was correct; it was handed an already-corrupted diff. Fixing a component does not fix the pipeline if something upstream mangles the input first.

[CRITICAL] app.py:6  (sql-injection)   ← the injection is on line 5
                                          line 6 is `return cur.fetchone()`

And each time, INV-3 reported green — the shifted line was still inside the hunk, so the grounding check happily accepted a finding pointing at the wrong place. A check can pass while the thing it checks is broken.

The counters (B5 / BD-2)

Findings were dropped silently. A lane whose every finding was hallucinated was byte-identical to a lane that genuinely found nothing: ok=True, findings=(), error=None. The reviewer reads "no findings" and moves on. Now dropped_ungrounded and dropped_malformed are tracked separately — different failures, different fixes — and produced_nothing_usable warns loudly.

Things worth stealing for the rest of the build

  • Ground truth must come from outside the code under test. The fixture is generated by real git diff and applies cleanly; the tests assert against the real post-image, not against the parser's own arithmetic. The original tests substring-matched joined text and asserted no line numbers at all — which is exactly how an off-by-N bug shipped.
  • A passing invariant is not proof. INV-3 went green through three separate mis-location bugs.
  • Test the seam, not just the unit. Every test called parse_diff on a string literal, so a bug living in the file read was invisible by construction.
  • mypy strict earned its place: it caught read_text(newline=) as 3.13-only when the package targets ≥3.11 — a crash for every user not on this machine's Python.

2. In round 5, the parser was correct and the renderer was correct, yet the tool still reported a SQL injection on the wrong line. Where did the corruption happen, and what does that tell you about where to look when a pipeline produces wrong output but every component tests clean?
